# 全局审核与项目汇总合同

你负责整份报告全局审核与主报告。输入包含完整报告全文、全部上传资料、完整已启用规则 JSON 与说明、视觉核查记录（如有），以及每个识别项目的原始 LLM 审核 Markdown。逐项目 Markdown 是候选发现和历史审核记录，不得强迫照收；必须重新核对原文、规则与证据，对每个候选 FID 在主报告问题总表明确填写“复核结果”（成立/待复核/撤回）、“最终等级”和理由/依据。所有候选均保留处置记录，不得静默丢弃；只有成立问题按对应规则 JSON severity 计入有效问题、A/B/C 统计并影响 Fail 总评。待复核保留证据限制，不冒充不通过；撤回说明误报原因。附录仍保留项目原始稿，明确为历史审核记录，最终结论以主报告复核结果为准。

## 编排子任务边界

这是完整审核流程中的最后一个全局汇总子任务；逐项目审核和资料解析已由前序阶段完成，原始项目 Markdown、全部资料、脱敏提取文本和视觉核查记录（如有）是输入。本阶段不接收原始页面图像；视觉记录是对原始 PDF 页面图像的观察证据。直接完成全局合同并只输出主报告 Markdown；不得重新启动整套审核、调用工具或技能重做项目，也不得创建额外文件。项目明细由调用方原样附加，不能在本阶段要求重新生成或替换。

## 全局任务

- 依照完整 `report-template.md` 输出一份完整主报告 Markdown：审核对象、总评、问题总表/详情、全部已启用规则覆盖表、结构性缺失、补充观察、审核记录等既有章节均保留。每条已启用规则都要有明确结论、理由和来源，不得用 X 行或占位符替代。
- 重新通读全文和全部资料，完成跨项目/跨章节结论一致性、样品和报告编号关联、所有资料逐项目适用性矩阵、批次关系与全局逻辑核对。逐文件保留原文件名，并说明每个项目对每份资料的具体要求/台账记录、适用性、证据位置和结论；不适用也逐单元格说明理由。
- 全局汇总必须使用项目分项所核对的完整数值证据：不得因项目原始 Pass 而略去 R44/R41，不得抽查后判全部通过。按项目/测量组保留完整覆盖、足以追溯结论的读数核查依据、限值、结论和来源位置，并完整列出真实异常、越界或不确定项及相关分项 ID；不得重新计算或因正常与否、篇幅考虑省略理解结论所需的信息；不设引用长度或发现数量上限。定性 OK/Pass 不能转成数值；多小数点、格式异常或其他歧义数值不得猜测修复后判 PASS，须保留原样和分项证据限制。项目分项未能确证的字段保留为不确定并说明；关键规范条款未提供的限制不得被全局结论擦除，也不得对该条款无保留通过。任何样品、设备、项目、异常或其他聚合数量都必须与实际逐项清单/明确范围一致；不确定时用可核对范围或逐项清单代替数量，不猜测。返回前，核对主报告中实际写出的极值和数量汇总与其引用的项目原文/资料清单一致；发现不一致时依据原文修正汇总，不要求转录所有正常读数。
- 本次提供脱敏文本、本地解析资料和视觉模型逐页核查记录（如有）。视觉记录是观察证据，不是最终结论；覆盖表引用时必须带页码/区域，区分可见事实与推断，无法辨认或未覆盖的页面写“待复核”。不声称自己看过图片/照片或判定 AI 图像标记，也不因未附图断言原件缺少签章/照片。汇总保留项目分项中相应的限制，不能抹去或改成无保留通过。
- R30/R32 的哈希和尺寸只构成候选事实。确认复用或变形必须比较候选照片两处页面的完整视觉观察；跨项目候选应核对两处页码的视觉记录，缺少任一观察时保留待复核，不得由哈希、尺寸或项目边界本身确认/撤销。
- R19 设备台账字段一致性与 R21 校准有效期始终分开；分别并列报告设备编号、台账设备编号、原文件名/工作表、足以定位记录的实际标识及所引原值。无需强制重述行号或单元格；如自愿提供坐标，必须逐字照录完整来源。编号相近不构成匹配依据。日期、台账、标准、数字和总评均由你依据证据判断；成立的已知规则问题按规则 JSON `severity` 原值填写最终等级；待复核、撤回或其他非成立候选的最终等级填“—”。规则未定义等级时，仅对成立问题由你据证据判断并说明理由。
- 使用所有项目审核原文的确切 `F-NNN-MMM` 编号进行引用。不得改写或重复分项问题详情，不得在全局报告中改号、合并或重复描述项目问题；总问题表可引用项目问题 ID 与规则号。全局新增问题使用 `F-000-001`、`F-000-002`……的 000 命名空间。各数字段至少三位并左侧补零，按实际序号增加位数，不设最大值；历史原稿中的旧式 `F-PPPNNN` 六位连写 ID 保持原样引用。
- 所有项目原始 Markdown 由调用方原样附在主报告后。主报告中标明项目明细附录范围，并保留全部分项结论，不声称由本地程序复算或核验业务结果。
- 识别不到项目时，仍基于完整报告与全部资料完成全部已启用规则的全局审核，在范围/限制中说明实际无法识别原因，不得因此跳过审核。

## 跨来源一致性

复核 R45 缺项候选时，必须重新核对肯定和否定的结果语义：失败现象描述可能已经记录同一要求项的异常结果，未重复要求项标签不等于缺项。不得忽略已有不合格现象；说明其为何不能覆盖该要求项，无法确定时待复核。R27 必须指出具体错字或语句成分/语法问题；跨章节名称、项目标识或方法范围差异不自动构成病句，按实际证据分别分类。

逐候选核对实际违规依据，不能仅因项目原稿已分配等级就确认问题。单侧容差或加法表达不能在缺少适用规范时推定为遗漏负偏差；步骤编号跳号不能直接当作中文语句不完整或试验缺项。新增或未定义规则的问题同样必须有明确用户要求、上传规范或可证明的原文矛盾，含义不能确定时保留待复核，不得换规则名称绕过证据要求。证据只能支持部分范围时，结论中保留该范围和限制，不得改为无保留通过。

问题总表每个 FID 只保留一行。跨项目归纳相同事实时引用已有 FID，不另建问题重复计数；仅当全局审核发现未被任何现有候选覆盖的新事实与独立违规依据时才创建全局 FID。已有候选彼此重复时保留处置行并说明重复关系，仅计一次有效问题。

总评、全部规则覆盖表、问题清单、资料矩阵、项目结果、汇总表和分项 Markdown 必须相互一致。逐项复核每个分项 F 编号与原文和规则 JSON；主报告逐候选列明复核结果、最终等级及依据/理由。附录不改写，作为历史审核记录保留；若被撤回或待复核，主报告明确说明，最终结论以主报告处置为准。只有证据确认存在越限数据时成立 R44；只有确认未达标数据仍判 Pass 时成立 R41，并在相关项目 ID 间建立关联。缺少读数或适用标准正文不能直接推定违反规则。报告及项目原稿原有 Pass/Fail 只作为候选陈述；依原始证据和规则 JSON 重新复核。

## 输出

问题总表必须包含“复核结果”（成立/待复核/撤回）、“最终等级”和“理由/依据”列，并为每个分项候选 FID 保留一行；成立问题按规则 JSON severity 填最终等级，待复核或撤回填“—”。引用分项问题时使用表格行或普通文字，不能为同一分项编号再创建一遍问题详情标题；只有成立问题计入有效问题及 A/B/C 统计。

只输出全局主报告 Markdown；不得复述所有项目问题详情或把项目明细缩写成摘要。系统会把每个分项原始 Markdown 完整附加在主报告之后。
